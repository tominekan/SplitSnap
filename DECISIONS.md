# DECISIONS

Decision and tradeoff report for the SplitSnap preliminary experiments. Entries were written at the moment each decision was made, and the **Evidence** lines were filled in once the corresponding run finished. Numbers quoted here come from files in `results/`.

---

## D01. Separate git repository inside the project folder
- Decision: run `git init` inside `SplitSnap/` instead of committing to the enclosing `/Users/tominekan/Code` repo.
- Why: the enclosing repo has no commits and hundreds of unrelated staged files. The task says to commit after each task, and also never to touch anything outside the project. A nested repo satisfies both.
- Tradeoffs: the parent repo will see `CV/SplitSnap` as an embedded repo if you later `git add` it there. You may want to push this repo on its own, or remove `SplitSnap/.git` and commit from the parent.
- Alternatives considered: (a) commit in the parent repo, which would sweep in unrelated staged files; (b) skip commits, which breaks the task instructions.
- How to test it: n/a (housekeeping).
- Evidence: `git -C .. status` was not modified; `git log` in this folder shows one commit per task.

## D02. Install Tesseract locally inside the project (micromamba, conda-forge)
- Decision: Tesseract 5.5.3 from conda-forge, installed into `tools/tess/` with a project-local micromamba. `src/common.py` points pytesseract at `tools/tess/bin/tesseract` when it exists, else falls back to a `tesseract` on PATH.
- Why: the task assumed Tesseract was already installed, but it was not. `brew install` writes to `/opt/homebrew`, outside the project folder, which the constraints forbid.
- Tradeoffs: ~250 MB in `tools/` (gitignored). Teammates who already have a system Tesseract can ignore it. Version may differ from a teammate's Homebrew Tesseract, which can shift CER slightly.
- Alternatives considered: (a) Homebrew (simplest, but writes outside the folder); (b) building from source (slow, same issue for leptonica); (c) skipping OCR (impossible).
- How to test it: run `python src/evaluate.py` on a machine with system Tesseract and compare `results/summary.csv`.
- Evidence: `tools/tess/bin/tesseract --version` prints `tesseract 5.5.3`.

## D03. Datasets and splits
- Decision: CORD v2 **test** (100) for reporting item-level metrics, CORD v2 **validation** (100) for developing parser rules by eye (never used for reported numbers); SRD split into a 30-image validation set (random, seed 0, among labelled images) for all tuning (preprocessing, Tesseract config) and a 168-image test set for reporting.
- Why: CORD is the only public set here with item-level labels; SRD is the only one with US restaurant photos and receipt corners. The task asked for a 30-image held-out SRD split. Using CORD validation for rule development keeps the CORD test numbers honest without spending any test images.
- Tradeoffs: 30 tuning images is small, so the chosen preprocessing could be noisy (a 1-2 point CER difference may not be significant). CORD's Indonesian receipts differ from US ones (currency format, language), so CORD item scores tell us more about the parser than about US restaurants.
- Alternatives considered: (a) k-fold cross-validation on SRD (more stable choice, 5x the OCR cost); (b) use the CORD train split (800) for tuning too, which only matters if we train something; (c) annotate a handful of our own US receipts with items, the best match to the real use case but no time tonight.
- How to test it: repeat the preprocessing selection with 3 different seeds for the SRD split and check whether the winner changes.
- Evidence: `results/logs/data.txt` (counts: CORD test 100 receipts / 268 priced items; SRD 198 images, 193 with text, val 30, test 168).

## D04. Image loading honours EXIF orientation
- Decision: load every image through `PIL.ImageOps.exif_transpose` before handing it to OpenCV.
- Why: SRD corner labels are in the EXIF-rotated frame (4 images otherwise have corners outside the image). Phones also store photos this way, so the app must do it anyway.
- Tradeoffs: none of note (a few ms per image).
- Alternatives considered: ignoring EXIF (OpenCV `imread` with `IMREAD_IGNORE_ORIENTATION`), which mislabels those images.
- How to test it: `python src/data.py` prints any corner outside its image; it prints none.
- Evidence: `results/logs/data.txt`.

## D05. CORD label conversion to our schema
- Decision: each `menu` entry with a `price` becomes an item `{name: nm, qty: first number in cnt (default 1), price: price}`; each priced `menu.sub` modifier (e.g. "COCONUT JELLY 4,000") becomes its own item; when `price` is missing we fall back to `itemsubtotal`; entries or modifiers with neither are dropped (19 of 287 menu+modifier entries in test, mostly unpriced modifiers such as "Less Ice", "+M", "=*LARGE*=="). `subtotal = sub_total.subtotal_price`, `tax = sub_total.tax_price`, `tip = sub_total.service_price` (Indonesian service charge plays the role of a tip in the bill split), `total = total.total_price`. Discounts, cash, change and card amounts are not in our schema and are ignored.
- Why: matches the output schema the app needs (line totals per item) and what is printed as a priced line, which is what an OCR-based parser can see.
- Tradeoffs: treating modifiers as separate items means a parser that merges a modifier into its parent line is penalized twice (one miss, one wrong price). Ignoring discounts means some ground-truth receipts fail our own checksum, so we also report the ground-truth checksum pass rate as a ceiling.
- Alternatives considered: (a) fold modifier prices into the parent item (closer to how a person splits a bill, but no longer a 1:1 match to printed lines); (b) keep CORD's full 30-class schema (more informative, but more than the app needs).
- How to test it: re-score with modifiers folded into parents and see whether parser rankings change.
- Evidence: `results/logs/data.txt`; ground-truth checksum pass rate in `results/summary.md`.

## D06. Number normalization depends on the currency, which is given per dataset
- Decision: `parse_amount(s, currency)`. For USD, the last `.` or `,` followed by exactly two digits is the decimal mark. For IDR, `.` and `,` are thousands separators and a trailing 2-digit decimal part is dropped (`"24,000.00"` -> 24000). The pipeline is told the currency (`IDR` for CORD, `USD` for SRD).
- Why: CORD writes 60 thousand rupiah as `60.000`; a US-style parser would read 60.0. In the app the locale is known from the phone, so passing it is realistic.
- Tradeoffs: a receipt in an unexpected format (European `12,50`) would be misread. Price regexes also differ per currency (USD requires 2 decimals, IDR requires 3-digit groups or 4+ digits), which makes the parser stricter, so it misses OCR outputs that dropped a separator.
- Alternatives considered: (a) auto-detecting the format per receipt from the majority pattern; (b) a learned field extractor (LayoutLMv3/Donut) which learns formats from data.
- How to test it: run the regex parser with auto-detection instead of the given currency on both datasets.
- Evidence: unit checks in `src/common.py` docstring; item price matches in `results/summary.md`.

## D07. Deriving SRD ground-truth totals from the transcription
- Decision: candidate lines contain `total`, `amount due`, `amt due` or `balance due` and end in a `d.dd` amount; lines with `sub total`, `tax`, `item`, `qty`, `discount`, `savings`, `tip amount` or `change` are excluded. The total is the largest candidate. It is marked unreliable (and the receipt skipped for total accuracy) when no candidate exists or the total is below the largest annotated subtotal.
- Why: SRD has no field labels. Taking the largest "total-like" amount handles receipts that print "Total" twice or print a pre-tip and post-tip total. The subtotal check rejects odd cases such as discounts or split checks.
- Tradeoffs: 171 of 193 labelled receipts get a total (22 skipped: mostly receipts with no printed total amount on the same line, or totals below subtotal). On receipts with a printed "total with tip", we would take that larger number as truth.
- Alternatives considered: (a) hand-labelling totals for all 193 (most accurate, about an hour of work); (b) last total-like line instead of largest (fails when tip suggestions or "total with tip" follow).
- How to test it: hand-check 20 random derived totals against the images; I spot-checked about 20 while writing the rule (e.g. 1001 -> 69.25, 1072 -> 21.69, 1150 -> 80.45, 1102 correctly rejected: subtotal 29.85 > total 16.24).
- Evidence: count printed by `python -c "from data import ..."` during development; the evaluation reports how many SRD test receipts had a usable total.

## D08. Traditional pipeline (classic CV + Tesseract) instead of an LLM/VLM
- Decision: every stage is hand-written classic CV or rules on top of Tesseract. No learned layout model, no LLM, no VLM, no paid API.
- Why: the course asks for a traditional baseline we can measure and explain, and every stage can be switched off as an ablation. It runs offline on a laptop (~0.2-1 s per image), costs nothing, and gives a floor that later learned methods must beat.
- Tradeoffs: much lower accuracy than modern document models on messy photos; rules are brittle across receipt formats (CORD vs US); lots of hand-tuned thresholds.
- Alternatives considered: (a) **Donut** (OCR-free encoder-decoder fine-tuned on CORD; reported ~90 tree-edit accuracy on CORD) would beat us by a wide margin on CORD but needs a GPU to fine-tune and generalizes poorly to US receipts without new labels; (b) **LayoutLMv3** on top of OCR boxes (token classification into menu.nm / price / total) would replace our hand rules in task 6 and needs labelled boxes (CORD has them); (c) a **VLM** (GPT-4o, Claude, Qwen2-VL) prompted for JSON would likely be the most accurate on US receipts with zero training but costs per call, needs network, and is hard to ablate. We would switch once the classic baseline is documented, starting with LayoutLMv3 as a drop-in for the parser.
- How to test it: run Donut (CORD fine-tuned checkpoint) and a VLM on the same CORD test / SRD test splits with our metrics.
- Evidence: B0 scores in `results/logs/score_B0.txt` (CORD item F1 0.213, SRD CER 0.393) show how far a naive traditional pipeline is from usable.

## D09. Tesseract configuration
- Decision: Tesseract 5.5.3, LSTM engine (default `--oem`), language `eng` for both datasets, one `image_to_data` call per image (word boxes + text rebuilt from Tesseract's block/paragraph/line ids). B0 uses the default page segmentation `--psm 3` (fully automatic). The psm is then treated as a tunable option in iteration 2 (D13).
- Why: psm 3 is what a naive user gets, which is the right baseline. One `image_to_data` call gives both the text (for regex/CER) and the boxes (for the layout parser) without running OCR twice.
- Tradeoffs: `eng` lacks Indonesian words, so some CORD item names are misread. psm 3 often splits a receipt into a name column and a price column as separate blocks, which destroys "name ... price" lines (visible on CORD validation: `Subtota]:` followed by no number).
- Alternatives considered: (a) `eng+ind` for CORD (better names, slower, and not the US use case); (b) `--psm 4` (single column of variable size text) or `--psm 6` (one uniform block), usually better for receipts; (c) a learned OCR (EasyOCR/PaddleOCR, task 8).
- How to test it: psm sweep on the SRD validation split (done in task 5, see D13); `eng` vs `eng+ind` on CORD validation.
- Evidence: `results/logs/score_B0.txt`; psm sweep in `results/preprocess_sweep.md`.

## D10. Regex parsing rules (baseline parser)
- Decision: per text line: (1) find a price at the end of the line (USD `d.dd` with optional `$` and thousands commas; IDR thousands-grouped or 4+ digit numbers), allowing a 1-2 letter tax flag after it; (2) if the line matches a keyword, fill that field, first occurrence wins, checked in the order subtotal (`sub total`, `subttl`, tolerant of `0` for `o`), tax (`tax`, `pb1`, `ppn`, `vat`, `pajak`), tip (`tip`, `gratuity`, `service`, `svc`), total (`total`, `jumlah`, `amount due`, `balance due`, `grand`); (3) skip payment/noise lines (`cash`, `change`, `card`, `visa`, `item`, `qty`, `%`, ...); (4) otherwise it is an item: optional leading 1-2 digit quantity (`2`, `2x`), the rest is the name, which must contain at least 2 letters. Rules were written up front and checked on CORD validation only.
- Why: this is the simplest rule set that implements the task's B0 definition, and it is easy to explain on a slide.
- Tradeoffs: depends entirely on Tesseract's line grouping; a name and its price split onto different lines is lost. "First occurrence wins" fails when a receipt prints a running subtotal twice (SRD 1001 prints "Sub Total" twice). Tip-suggestion lines are skipped via `%`, which also drops lines like "PB1 10%" unless they matched tax first (they do, since keywords are checked first).
- Alternatives considered: (a) layout-aware rows from word boxes (task 6); (b) a CRF/LayoutLMv3 token classifier trained on CORD train (learns field types instead of keywords).
- How to test it: compare regex vs layout parsing on identical OCR output (done in task 6/7).
- Evidence: CORD validation B0: item P 0.474 / R 0.116 (development only). Test numbers in `results/summary.md`.

## D11. Pipeline engineering: OCR cache and parallelism
- Decision: run images in 8 worker processes; cache each image's OCR output (text, boxes, stage timings) in `data/cache/ocr/` keyed by (dataset, image, rectify mode, preprocessing options, psm). Runtime per image = rectify + preprocess + OCR + parse time measured when the OCR stage actually ran (stored in the cache entry), so cached reruns report the original timings.
- Why: the ablation re-runs the same OCR many times (regex vs layout share OCR); caching makes `python src/evaluate.py` cheap to rerun. Timings stay honest because they are stored, not re-estimated.
- Tradeoffs: timings are measured with 8 processes in parallel, so per-image wall time is somewhat higher than single-process. Stale cache is possible if you change rectify/preprocess code without changing options: use `python src/evaluate.py --no-cache` (wipes `data/cache/ocr`).
- Alternatives considered: no cache (simplest, ~4x slower to rerun); caching only parser inputs in memory.
- How to test it: run `--no-cache` and compare the table.
- Evidence: `results/logs/pipeline_B0.txt` (298 receipts in 20 s).

## D12. Rectification method, plausibility check, margin and fallback
- Decision: detect the receipt on an 800-px-high copy using three masks tried in order: (1) "paper" = bright (Otsu on HSV value) AND low saturation (S < 60), opened 5x5 and closed 25x25; (2) Otsu on grayscale, closed 15x15; (3) Canny (50/150) dilated. For each mask, take the 5 largest external contours, take the convex hull, approximate with `approxPolyDP` at epsilon 2%, 3%, 5% of the perimeter, and accept the first convex 4-gon covering 15-97% of the image. Then: expand the quad outward by **6%** (corner-to-centroid distance), and run a **plausibility check** (every corner angle within 85-95 deg, opposite sides within 10% in length). A plausible quad gets a perspective warp; an implausible one is replaced by its **axis-aligned bounding box (a plain crop, no shear)**. If no 4-gon is found at all we **fall back to the original image**. Every prediction JSON records `rectify_info` (method, quad, fallback); `results/logs/rectify.txt` lists fallbacks and crops. For scoring, a fallback counts as predicting the full frame.
- Why: the classic "largest 4-point contour" recipe the task asked for, plus fixes for what broke on the validation splits:
  - Dark wood tables confuse Canny and white trays confuse a grayscale threshold. Receipt paper is the brightest **and** least saturated region, and the convex hull removes notches where the paper is crumpled or covered (validation mean IoU 0.798 -> 0.885, `results/logs/rectify_variants_val.txt`).
  - The first full pipeline run showed that **rectification made OCR worse**: CORD validation item F1 0.349 -> 0.186, SRD validation CER 0.312 -> 0.340 (psm 6, no preprocessing). Looking at the images: (a) a quad with IoU ~0.85 often clips the price column; (b) when the receipt runs off the frame or a shadow merges with it, one wrong corner makes the warp **shear** the receipt, so prices drift onto the neighbouring text row (CORD validation_035). The 6% margin fixes (a), the plausibility check + crop fixes (b). Variants are in `results/logs/rectify_margin_val.txt`.
- Tradeoffs: the 85 deg threshold is strict, so most real perspective photos (122 of 168 SRD test images) only get the bounding-box crop, not a true perspective correction. Rectification is effectively "crop to the receipt" plus a warp for near-frontal photos. The margin and the crop lower IoU against the tight labels (test IoU of the region used 0.786 vs 0.832 for the raw detector). The settings were chosen on both validation splits (SRD validation CER and CORD validation F1) from 11 variants, so there is mild selection bias; CORD test and SRD test were not used. The variant with check but no crop was slightly better on CORD validation (F1 0.379 vs 0.365) and worse on SRD (CER 0.285 vs 0.273); I picked the crop variant because SRD is closer to the real use case and the CORD difference is within noise (~230 items).
- Alternatives considered: (a) Hough lines + intersecting the 4 dominant lines, which handles receipts running off the frame (the main source of bad corners); (b) a learned corner/segmentation model (e.g. a small U-Net or a DocAligner-style corner regressor trained on SRD corners + CORD roi), which would handle clutter and curl so that the warp can be trusted; (c) dewarping for curled paper (page dewarping with text-line fitting). We would switch to (b) first, because the oracle row shows how much a correct warp is worth.
- How to test it: compare our rectification with oracle rectification (labelled corners) on the same downstream metrics; if the gap is large, a better detector is worth the effort. Also check per image whether the CER change correlates with IoU.
- Evidence: `results/rectify_summary.json`, `results/logs/rectify.txt`. **SRD test (168): detection rate 0.929 (15 of 198 images fell back, several of them receipts that fill the frame); raw detector mean IoU 0.832, IoU >= 0.9 on 48%, corner error 0.050 of the diagonal; region actually used (after margin / crop) IoU 0.786; full-frame IoU would be 0.688.** Some labelled corners hug the printed text rather than the paper (SRD 1004), which caps the measured IoU. Downstream effect: see the `+rectify` and oracle rows in `results/summary.md`.

## D13. Preprocessing options, psm, and how the winner was picked
- Decision: five options, applied in this fixed order when enabled: **denoise** (OpenCV non-local means on grayscale, h=10, before upscaling to keep it cheap), **upscale** (resize so the median character height, from connected components of an adaptive-threshold text mask, reaches ~30 px; factor clipped to 1-3.5x, longest side <= 4000 px), **CLAHE** (clip 2.0, 8x8 tiles), **deskew** (angle in [-5, 5] deg at 0.25 deg steps maximizing the variance of the row profile), **binarize** (none / OpenCV adaptive Gaussian block 31, C 15 / Sauvola window 31, k 0.2). Tesseract **psm 3 / 4 / 6** is swept alongside. All 3 x 48 = 144 combinations were scored by mean CER on the 30-image SRD validation split (after our final rectification, D12); the lowest wins. Chosen: **psm 4 + denoise + upscale + CLAHE + deskew + Sauvola** (validation CER 0.208, vs 0.270 for the best psm without preprocessing and 0.342 for psm 3).
- Why: a full grid is small enough (~12 min), avoids order effects of greedy selection, and lets us report each option's effect alone and on average (marginal effect), as the task asked. Character height and deskew use a local threshold because a global Otsu mask failed under uneven lighting (SRD 1001 estimated 5 px characters and a 5 deg skew on a straight receipt).
- Tradeoffs: picking the best of 144 configurations on 30 images overfits. The clearest sign: with the first version of rectification the same sweep picked psm 6 + denoise + upscale + CLAHE + Sauvola (CER 0.231), and after the rectification change it picked psm 4 with deskew added. The robust pattern is **denoise + upscale + Sauvola, with psm 4 or 6**; the rest is noise-level. The chosen pipeline is ~3.5x slower than no preprocessing (1.72 vs 0.50 s/img on validation, measured with 8 parallel workers). CLAHE alone hurts (+0.033 CER) and hurts on average (+0.045), yet it is in the winning combination, an interaction with Sauvola that I would not trust without more data.
- Alternatives considered: (a) greedy forward selection (cheaper, order-dependent); (b) a learned enhancement/binarization network (e.g. DE-GAN or a U-Net document binarizer), better on shadows and crumpled paper, needs training data; (c) skipping preprocessing and switching to a learned OCR (task 8), which is usually more robust to raw photos.
- How to test it: repeat the sweep on 3 different random 30-image validation splits (or 5-fold CV) and check whether the winner and the marginal effects are stable; report test CER for the top 3 validation combinations to see the spread.
- Evidence: `results/preprocess_sweep.md`, `results/preprocess_sweep.csv`, `results/preprocess_best.json`, `results/logs/preprocess_sweep.txt`. Each option alone at psm 4 vs grayscale only: denoise +0.005, upscale -0.025, CLAHE +0.033, deskew -0.008, adaptive -0.028, Sauvola -0.023 CER. Marginal effects across the psm-4 grid: denoise -0.053, Sauvola -0.044, adaptive -0.013, upscale -0.012, deskew +0.001, CLAHE +0.045.

## D14. Layout-aware parsing: row grouping from word boxes
- Decision: ignore Tesseract's own line structure and regroup its words into rows by vertical center: sort words by center y, and a word joins the current row if its center is within **0.5 x the median word height** of the row's running mean center. Within a row (left to right) the right-most price token is the line price (a 1-2 letter tax flag after it is allowed; two tokens are joined only when they look like a split price, e.g. `$ 9.39` or `60. 000`, to avoid turning `1 28,000` into `128,000`; stray symbols glued to a price such as `«$1.40` are stripped first, a rule added after the demo notebook showed it on one receipt). A leading `2` / `2x` token is the quantity; name = remaining tokens that contain letters (drops unit prices like `@28,000`). A priced row without a name (CORD's `2 x 25,000   50,000` under the item name) borrows the name from the previous unpriced text row. Keyword rows use the same keyword lists as the regex parser (D10); a keyword row without a price takes the next row's price if that row is only a number.
- Why: the main failure of B0 is that Tesseract (especially psm 3) puts the name column and the price column in different blocks, so "name ... price" never appears on one text line. Word boxes keep the geometry, and rows on a rectified receipt are horizontal, so a 1-D clustering of y centers is enough.
- Tradeoffs: assumes the receipt is roughly level after rectification. Skew greater than about half a line height across the receipt width merges or splits rows, which is why rectification and parsing interact. A greedy 1-D clustering cannot separate two lines that touch (tight line spacing). Names borrowed from the previous row can attach the wrong name when a modifier line sits in between. Precision drops a bit compared to regex because more rows look like items (e.g. phone numbers ending in 4+ digits on CORD).
- Alternatives considered: (a) Tesseract's own line ids with psm 4/6 (simpler, but splits wide-gap lines); (b) DBSCAN on y centers, or fitting text-line baselines, which handles slight skew; (c) **LayoutLMv3** (or a GNN over word boxes) trained on CORD's labelled boxes to tag each word as name / count / price / total, which learns these rules instead of hand-coding them and handles multi-line items; this is the natural next step once we accept training on CORD train.
- How to test it: regex vs layout on the same OCR output (the `+rectify+preprocess` vs `+rectify+preprocess+layout` rows); sweep the row tolerance on CORD validation.
- Evidence: CORD validation, B0 OCR: regex F1 0.186 vs layout F1 0.250 (tolerance 0.3: 0.219, 0.5: 0.250, 0.7: 0.248; 0.5 was chosen before looking and is also the best). Test numbers in `results/summary.md`.

## D15. Item matching rule and thresholds
- Decision: an extracted item matches a true item if the **prices are exactly equal** (after currency normalization, |diff| < 0.005) and the **normalized names** (lowercase, only letters/digits/spaces, collapsed whitespace) have rapidfuzz `ratio >= 0.8`. Matching is one-to-one, greedy by similarity. Precision = matches / predicted items, recall = matches / true items, both **micro-averaged** over all receipts (F1 from those). Quantity is extracted but not part of the match.
- Why: the price is what matters for splitting a bill, so it must be exact; names only need to be recognizable, and OCR rarely gets every character right (0.8 tolerates about one error in five characters). Micro-averaging weights every item equally, so receipts with many items count more, which matches how much splitting work they represent.
- Tradeoffs: an item with a perfect name and a single wrong digit in the price counts as both a miss and a false positive. Short names (`TEA`) need an exact match; long names tolerate several errors. Quantity errors are invisible to this metric.
- Alternatives considered: (a) CORD's official tree-edit-distance accuracy (standard for Donut-style comparisons, harder to explain); (b) separate name-only and price-only matching to diagnose which half fails; (c) a lower name threshold such as 0.6.
- How to test it: re-score with thresholds 0.6/0.7/0.9 and with price-only matching; if rankings between configurations change, the conclusions depend on the threshold.
- Evidence: see `results/summary.md`; per-receipt F1 in `results/cord_per_receipt_f1.csv`.

## D16. Checksum and its tolerance
- Decision: a receipt passes if (1) the item prices sum to the subtotal and (2) subtotal + tax (+ tip) = total, both within **0.5% of the total**. If total, subtotal or items are missing, the checksum is not computed and counts as a fail. The checksum is reported, not used to correct the output.
- Why: it is a label-free self-consistency signal the app could use at run time to decide whether to trust the parse or ask the user. 0.5% absorbs rounding (e.g. tax rounding) without accepting a wrong digit in most cases.
- Tradeoffs: real receipts have discounts, service charges, rounding and "inclusive tax" lines that break the identity. Even CORD ground truth fails it often (reported as a ceiling in `results/summary.md`). A false pass is possible when two errors cancel. On large rupiah totals, 0.5% is up to a few thousand rupiah.
- Alternatives considered: (a) an absolute tolerance (e.g. 1 cent USD), stricter and currency-specific; (b) using the checksum to choose among parse hypotheses (e.g. try alternative digit readings until it passes), a cheap accuracy boost we have not implemented.
- How to test it: compare checksum pass vs. actual exactness of items + total on CORD: precision of "pass" as a predictor of a fully correct receipt.
- Evidence: `results/summary.md` (checksum column and ground-truth ceiling).

## D17. Choice of metrics
- Decision: CORD: item P/R/F1 (D15), exact-match accuracy for subtotal/tax/total over receipts where the field exists, checksum pass rate. SRD: mean per-image **CER** of the full OCR text vs the transcription (both lowercased, whitespace collapsed, empty lines dropped; via `jiwer.cer`; an empty prediction counts as CER 1.0), median CER, total-amount accuracy on receipts with a derived total (D07), and the rectification metrics (detection rate, IoU, corner error / image diagonal). Both: mean runtime per image.
- Why: CORD has item labels, so we measure what the app needs. SRD has only transcriptions, so CER measures OCR quality (what rectification and preprocessing are supposed to improve), and total accuracy is the one field we can derive. Lowercasing and whitespace normalization stop us from penalizing formatting differences the parser does not care about.
- Tradeoffs: CER is sensitive to reading order: if Tesseract reads a price column after the name column, CER is high even when every character is right. That penalizes psm 3 more than it would hurt a layout parser. Mean CER is pulled up by a few near-total failures, so the median is also reported. CER can exceed 1 when the OCR hallucinates a lot of text.
- Alternatives considered: (a) bag-of-words F1 (order-free, so it separates recognition errors from reading-order errors); (b) WER; (c) a field-level metric for SRD after hand-labelling a few fields.
- How to test it: compute order-free bag-of-characters/words F1 alongside CER and check whether configuration rankings agree.
- Evidence: `results/summary.md`.
